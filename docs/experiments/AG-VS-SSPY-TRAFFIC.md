# ssag(agentgateway) vs sspy(旧 Python 网关) 流量实测对比

- 生成时间：2026-11-17 11:40（Asia/Shanghai）
- 数据源：agentgateway 与旧控制面的 `request_logs` 本地只读快照（分别为 345 行 / 23,420 行）。
  两条链路均来自本地只读快照；不上传原始数据。
- 对比窗口：**2026-11-17 00:23 – 11:02（北京）**，10.64h，两个库的重叠区间
- 属性：**观察式对比，不是受控 A/B**。两个网关同时独立服务不同客户端（旧：127.0.0.1 的 agent 客户端；新：deepseek-harness），
  上游同一家（厂商与域名隐去，模型 deepseek-flash）。输出 token 分布不同，只在"特征相近"的桶里做结论。

## 1. 总体（同窗口）

| 维度 | sspy | ssag | 说明 |
|---|---|---|---|
| 请求数 | 1,205 | 345 | ssag 只有约 1/3.5 流量 |
| 首字 TTFT p50 | **5,231 ms** | **5,081 ms** | 基本持平 |
| 首字 p90 | 22,694 ms | **13,464 ms** | ssag 尾部好 41% |
| 首字 p99 | **39,373 ms** | 44,252 ms | ssag 尾部更差（样本少） |
| 首答 TTFA p50 | **11,473 ms** | *未记录* | ssag 只记 TTFT，无"首个非推理 token" |
| 总耗时 p50 | 12,113 ms | **8,281 ms** | ssag −32% |
| 总耗时 p90 | 42,538 ms | **20,474 ms** | ssag −52% |
| 总耗时 p99 | 116,368 ms | **56,342 ms** | ssag −52% |
| 输出 tokens p50 | 840 | 667 | 工作量不同，需归一 |
| 输入 tokens p50 | 110,173 | 105,051 | 同为 10 万级长上下文 |
| 端到端吞吐 p50 | 92.8 tok/s | 91.0 tok/s | 持平 |
| 上游缓存命中率 | 79.6% | 91.6% | ssag 更高 |
| 错误率 | 10.71% | 11.01%（**剔除自伤后 1.16%**） | 见 §4 |
| 并发峰值 / 均值 | 11 / 0.59 | 3 / 0.09 | 都没被压过 |
| 峰值请求密度 | 403 req/h | 77 req/h | |

## 2. 归一化后的同桶对比（输入 60–120k 且输出 400–1200 tokens）

| 指标 | sspy (n=243) | ssag (n=66) | 变化 |
|---|---|---|---|
| 首字 p50 | 5,070 ms | **4,652 ms** | −8% |
| 首字 p90 | 16,807 ms | **10,603 ms** | −37% |
| 总耗时 p50 | 9,893 ms | **7,555 ms** | −24% |
| 总耗时 p90 | 19,456 ms | **13,459 ms** | −31% |
| 总耗时 p99 | 39,572 ms | **20,684 ms** | −48% |

**结论：在同等上下文/输出量级下，ssag 的首字略快、尾部明显更短、总耗时领先 24–48%。**

## 3. 按缓存命中率分桶看首字（关键异常点）

| 上游缓存命中 | sspy 首字 p50 | ssag 首字 p50 | 差异 |
|---|---|---|---|
| 0–50% | 10,215 ms | **7,925 ms** | ssag −22% |
| 50–80% | 8,419 ms | **3,354 ms** | ssag −60% |
| 80–95% | 4,704 ms | **4,057 ms** | ssag −14% |
| >95% | **3,792 ms** | 4,701 ms | ssag **+24%** |

高命中率桶里 ssag 反而变慢，说明两者对上游 prompt cache 的利用方式不同（旧网关的请求形状更稳定 / 新网关的请求可能因 header 或前缀抖动丢失部分命中收益），**这是目前唯一对 ssag 不利的信号，值得单独立项验证**。

## 4. 稳定性

sspy（窗口内 129 次失败）：
- `UPSTREAM_RATE_LIMITED` 80 次（429，上游限流，真实压力）
- `UPSTREAM_ERROR` 46 次（502）
- `NO_AVAILABLE_CHANNEL` 2 次、`UPSTREAM_TIMEOUT` 1 次

ssag（窗口内 38 次失败）：
- `backends required DNS resolution which failed` **34 次** —— 全部集中在 19:48Z（北京 03:48）那一批，
  attributes 显示上游 endpoint（域名隐去），10ms 内返回 503 `NoHealthyBackend`。
  **属于我们自己配置/网络路径的自伤**（旧网关走的是 hosts/relay 固定路径，不依赖 DNS），不是数据面缺陷。
- `Connect: deadline has elapsed` 2 次、无 API Key 401 1 次、空错误 1 次。

**剔除 DNS 自伤后 ssag 错误率 1.16%**，显著优于 sspy 的 10.71%；但 ssag 从未承压（峰值 3 并发），该结论只在低负载下成立。

## 5. 卡点判断（"卡在哪"）

1. **首字主要卡在上游 prefill，不在网关**：输入 p50 约 10 万 tokens，即便缓存命中 91.6%，首字仍要 4–5s；
   网关侧差异（8%）远小于 token 量带来的差异。
2. **长尾同样来自上游**：两个网关的 p99 首字都在 40s 上下，与并发/网关排队无关（并发均值都 <1）。
3. **ssag 的 503 是 DNS 依赖问题**：旧网关有 hosts 钉住/relay 路径，ssag 直接依赖系统 DNS，解析失败即整批 503。已在 attributes 里定位到具体 endpoint。
4. **容量未被验证**：ssag 峰值并发 3、峰值 77 req/h，与旧网关峰值 403 req/h、11 并发不是一个量级，**不能据此说 ssag 更好或更稳**。

## 6. 结论与下一步

- 用户体验维度（首字/总耗时/尾部）ssag **不劣于且总体优于** sspy，尤其在总耗时 p90/p99 上领先一档。
- 吞吐（tok/s）两者持平；**解码速度不可直接比较**——旧库的 completion_tokens 含推理 token，且"答案"常以最后一整块发出
  （旧库 ttfa→ttlt 中位数仅 2ms），所以旧 decode tps 被严重低估，不要拿"318 vs 85 tok/s"当结论。
- 可信的差距仍需要 **受控 A/B**：同一客户端、同一 prompt 集、同一并发，分别打 3680 与 3691，记录逐 chunk 时间戳。
- 两个低成本改进：
  1. ssag 增加"首答（首个非 reasoning token）"埋点，否则推理模型的首字对比意义有限；
  2. 修掉 ssag 的 DNS 依赖（hosts/relay 或重试），34 次 503 可归零。
